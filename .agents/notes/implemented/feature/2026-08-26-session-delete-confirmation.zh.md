# Agent Note: 会话删除需要二次确认

Status: implemented

[English](2026-08-26-session-delete-confirmation.md) | 中文

## 问题

会话行的 Delete 操作直接提交：菜单里一次点击就经 `ctx.sessions.delete` 物理移除会话日志与整棵子代理树（[[2026-08-19-session-deletion]]、[[2026-08-23-stop-then-delete-session-deletion]]）。工作区删除早已打开说明后果并阻止重复提交的确认对话框（[[2026-07-27-workspace-registration-deletion]]），两个行操作里更具破坏性的那个反而成了唯一没有防护的，行菜单里的一次误点击在设计上不可挽回。

## 决策

会话删除复用工作区删除确立的浏览器持有确认模式，全部位于 `@deepseek-ai/dsh-client-ui-workspace` 内：

- 行菜单的 Delete 项打开 `Modal` 而不是直接提交。该项获得 `danger: true`，与工作区菜单的破坏性样式一致；归档因非破坏性保持无样式且不经对话框。
- 行在 id 之外同时派发显示标题（`onDelete(id, title)`），对话框的描述因此能像重命名对话框预填那样点名确切的行。
- 对话框说明不可逆性——消息日志与整棵子代理树被永久移除、操作无法撤销——并提供取消与删除。请求在途时两个控件都禁用、重复确认被忽略；Escape 与 Close 不能关闭在途删除。
- 失败时对话框保持打开并在其中渲染错误（旧的列表区告警席位已移除——现在所有删除失败都发生在对话框内）；取消可关闭失败的对话框而不重试。
- 仅 RPC 成功不关闭对话框：浏览器等到其 `useSessions` 投影丢弃被删 id 才关闭，与工作区对话框相同的回声落地关闭，被删行不会闪回一帧。

线上协议、host 与删除服务未触动；只有呈现接缝改变。

## 备选方案

- **保留直接提交、只守护当前会话**——否决：每个持久会话的日志同样不可恢复，与工作区删除对齐的诉求是一条统一规则。
- **原生 `confirm()`**——否决：应用的对话框词汇是 `ui-primitives` 的共享 `Modal`；工作区流程已经验证了组合模式连同焦点、Escape 与 Close 处理。
- **RPC 成功即关闭对话框**——否决：一帧过期的 React 会在下一次手势期间复活该行；投影落定的关闭正是对这一竞态的既定修法。
- **带模式开关复用工作区删除对话框**——否决：两份拷贝在文案、目标键（`WorkspaceId` 对 `SessionId`）与回声来源（`useWorkspaces` 对 `useSessions`）上各不相同；共享抽象会为约 40 行平行结构耦合两个独立的行生命周期。

## 验证

`rows.client.spec.tsx` 钉住 danger 样式与 `(id, displayTitle)` 派发。`workspace-browser.client.spec.tsx` 钉住完整对话框生命周期：菜单只打开对话框不调用操作、描述点名该行并说明不可逆、重复确认只提交一次、在途时两个按钮禁用、在途状态渲染、Escape/Close 无法在途关闭、RPC 成功后对话框保持打开直到会话投影丢弃该 id、拒绝渲染在对话框内且取消可关闭、提交前的取消/Escape/Close 永不删除。

## 结果

- 一次菜单点击不再能销毁会话日志；删除的唯一路径是对话框的删除按钮。
- stop-then-delete 笔记的「UI 内告警」结果现在指明对话框是告警的居所，而非列表区。
- 删除拒绝语义不变：处置后仍存活的成员仍会拒绝整个操作，现在显示在可关闭的对话框内。
