# Agent Note: The pi-ai model list is a fixed role mapping — five roles plus a fallback, prefilled from the catalog and filled by 获取模型列表

Status: implemented

English | [中文](2026-08-29-models-fixed-role-mapping.zh.md)

## Problem

The pi-ai editor's model list was an open-ended catalog editor, borrowed from the DeepSeek family: arbitrarily many rows, each editing an id, a display name, capacities behind a disclosure, and modality toggles. The user's request names cc-switch's mapping posture instead — "模型映射需要支持以下几个字段 模型角色/显示名称/实际请求模型/声明支持1M", "每个提供方都需要内置好一些配置信息，如提供方名称/API地址/API格式/提供方的模型", and a provider logo the user picks. A provider is not a catalog of rows the user curates: it is a fixed set of roles the harness's model picker addresses by name, plus one default fallback when a request names no role, and a provider being added should open with what its preset already knows rather than an empty form. An open row list cannot express the roles, and a create flow that discards the catalog's own facts makes the user retype them.

## Decision

`ModelListEditor` renders six fixed rows — the five roles `Sonnet`, `Opus`, `Fable`, `Haiku`, `Subagent`, then one default fallback model — as a five-column table: the role label, the display name (`name`), the request model id (`id`), the fetched-model pick, and the 1M declaration (`contextWindow: 1_000_000`). Every track resolves without measuring content (fr shares, a fixed picker track), because each row is its own grid and a content-sized track would drift between rows — the column alignment a table of inputs owes.

- **A role row's entry carries the role in its own `role` field; the display name is a separate fact.** A filled Sonnet row stores `{ id, role: 'Sonnet', ... }`, and the name column edits the entry's `name` independently — cc-switch's field set verbatim. The fallback row's entry is bare (`{ id }` — no role, no name): the picker then shows its id, which is what reads as "the model itself". Rows find their entries by `role` field, with an entry whose `role` is absent but whose `name` equals the role still recognized as that role's entry — the spelling the mapping wrote before the field existed, kept readable so a stored profile survives the upgrade. An entry matching no row — a field a future schema adds, or one hand-written in `settings.yaml` under some other role — is neither shown nor dropped: the mapping manages its six rows and leaves every other entry alone, the same structural openness the DeepSeek catalog editor's rows keep.
- **An empty mapping means the route's built-in catalog, and clearing a row removes its entry.** A row is only ever filled deliberately; emptying one splices its entry out, while the mapping header's reset affordance — offered while the user layer owns the array — hands the whole array back to the adapter. Two semantics for two intents: an empty override is not the same gesture as restoring inheritance.
- **The 1M declaration is a checkbox, on the roles that can grow one.** Sonnet, Opus, Fable, and the Subagent and fallback rows offer it; Haiku's row renders a dash instead (its class of model never grows one), and the Subagent row's name column says it never reaches the picker. Checking the box writes `contextWindow: 1_000_000`; a capacity discovery or the catalog disclosed lands the same way, so a 1M model shows its declaration checked. Other capacities stay plain facts the adapter reports — no per-row capacity inputs, because the adapter's route-level fallbacks size whatever configuration leaves out.
- **管理与测试 is the endpoint's own action, at the base-URL field's label row.** The fetch entry point sits at the API address field's right edge (the mapping header keeps a second one), disabled while the form's key is refused — asking with a key the form has already rejected spends a round trip to be told what the field already says. The create card additionally requires an endpoint to exist: a provider being declared has no route yet, so the typed endpoint is the only thing an interrogation could go on, and the button's own title names that gate.
- **Opening the dialog is the test request.** `ManageTestDialog` — titled 管理与测试 — mounts per open, so the interrogation runs once on mount. It asks `llm.discoverModels` about the endpoint **the form currently shows**: a base URL edited but not yet saved, a key typed but not yet stored, the protocol the form names. A route the adapter already describes answers from its own registry, so an existing provider's card can ask with no endpoint at all; only a draft with neither a route nor a base URL has nothing to ask about. The listing shows each candidate's display name beside its id and the capacities the endpoint disclosed. The reply's arrival is an event of its own: the round-trip time prints under the busy line, and a transient top banner — the `useModelFetchOutcome` hook both provider forms share — reports how many models arrived, so a two-hundred-model listing answers "did it work" without scrolling one.
- **The reply is candidates the user picks from, never configuration written behind them.** Candidates the endpoint already serves — ids present in the current mapping — start unchecked, so an adoption never rewrites a row the user already placed; select-all/deselect-all toggles the whole listing. Whatever the provider disclosed rides along into the row a candidate fills (its `contextWindow`, `maxTokens`, and input modalities onto the pi-ai profile's own `input` field — the wire's role `kinds` has no pi-ai counterpart and is not carried), and the candidate's own display name rides along too, because the name column is exactly where the endpoint's spelling belongs.
- **Adoption fills empty rows in display order — Sonnet first, the fallback last.** `adoptIntoMapping` skips a candidate whose id is already served. A full mapping adopts nothing: the adopt button is disabled with the `mappingFull` copy as its title, explaining itself rather than closing over a silent no-op.
- **Every fetched candidate also lands in the row's own pick menu.** The reply is handed to the form the moment it arrives (`onFetched`), so the pool survives the dialog closing without an adoption. Once a listing exists, each mapping row carries a chevron in the column before its 1M declaration; opening it lists the endpoint's whole catalog — id beside the endpoint's own display name — and one pick fills the row with the same write `pickIntoRow` performs: id, display name, the 1M declaration when the candidate's own context window is 1M, and every disclosed capacity. A hand-picked row is a deliberate fill, so an entry the row already held is replaced — the same write typing the id by hand makes, minus the transcription. Rows with nothing to list render no picker: an unfetched provider shows no controls that would only say "fetch first".

Each provider route also ships the facts its preset knows, and the form opens on them:

- **`LlmConfigurableProvider` carries `catalogBaseURL`, `catalogApi`, and `catalogModels`.** The pi-ai adapter fills them from its installed catalog — the built-in endpoint, the one protocol all the route's models share (absent when they disagree), and the models themselves in catalog order. They cross the wire as fields of `ConfigurableProviderView`, validated by the apiproxy schema, absent for a route the catalog knows nothing about.
- **The add flow prefills the form from the picked preset.** `ProviderEditor` opens with `prefill`, seeding the draft's display name, base URL, and protocol, and the mapping through `prefillMapping`: each role takes the first catalog model whose id names it (sonnet, opus, …), the fallback takes the first model no role consumed, and the catalog's names and capacities ride along. Rows already filled stay; an edit flow leaves everything untouched so an untouched form writes nothing. The cleared base-URL field's placeholder shows the catalog endpoint as "provider default".
- **A provider's logo is a vendored SVG mark, chosen per provider.** `ProviderLogo` renders the profile's own `icon` field first, else the built-in mark its route id maps to (`ROUTE_ICONS`), else the display name's first character on a palette color hashed from the route id — the letter avatar the card grid already used, kept as the fallback so an open route set needs no assets to ship. The SVGs and their display names are vendored from cc-switch's icon set in `provider-icons.ts`.
- **The icon is picked from a dialog.** `IconField` centers the logo button above the Provider ID on the create card and atop the editor form; clicking it opens `IconPickerDialog`, a searchable grid of the vendored marks with a preview, a restore-default action that clears the profile's `icon` (a shipped route returns to its built-in mark), and the write landing on the profile's `icon` field like any other edit. The dialog spans most of a settings pane's width (`width: min(760px, 100%)`) so the set reads as a grid rather than a strip, and it caps at the viewport height with the same content/body `min-height: 0` chain the edit and pick dialogs use, so a short window shrinks and scrolls the grid instead of growing the card past the fixed overlay and leaving its footer below the screen. The width must ride the dialog's own `width`, not a `max-width`: the Modal's card declares `width: min(380px, 100%)`, and a cap cannot widen it — measured in chromium, the picker rendered 380px while its rule said `max-width: 760px`. The scrolling grid reserves the scrollbar gutter (`scrollbar-gutter: stable`), because the theme's space-taking bar would otherwise cover the rightmost icon cells — the same reservation every scroll container in the section makes.
- **The API protocol dropdown spans its field.** The `select` input takes the field's full width (`select.input { width: 100% }`), matching every other control on the form instead of capping at its content.

Locale keys in both languages: `modelMapping`, `defaultFallbackModel`, `mappingFull`, `modelRoleLabel`, `requestModelLabel`, `modelOneMHeader`, `subagentHiddenName`, the `icon*` set for the picker, `fetchModels` (the mapping header's button), and the manage-and-test set — `manageAndTest` (the base-URL field's button and the dialog's title), `manageTestDescription`, `fetchToast` (`{count}`), `fetchLatency` (`{ms}`), and `modelPickerLabel` (each row's chevron).

## Alternatives considered

- **Keep the open-ended catalog editor** — rejected: the user named the four columns and the roles explicitly. A role is what the harness's model picker addresses by name; an arbitrary row list offers no place a role's model id belongs, and every provider form would make the user re-derive which row is which role from display names alone.
- **Store the role as the entry's display name** — rejected: the name column is a fact of its own. Overloading `name` to carry the role leaves no place for the display name the endpoint or the user wants the picker to show, and reading a stored profile back would have to guess which names are roles.
- **Editable capacities per mapping row** — rejected: the adapter's route-level fallbacks already size a model the entry describes by id alone; discovery carries disclosed capacities into the entry. The 1M declaration is the one capacity with a checkbox, because it is the claim the user owns — the endpoint's disclosure fills it, and a hand-check asserts what the endpoint did not say.
- **Adopt every discovered candidate on fetch** — rejected: the reply is candidates the user picks from. Writing configuration behind the user's back would re-point a role's model without the user ever seeing which id landed there, and a listing of two hundred models would overwrite a mapping the user had tuned.
- **Prefill nothing and let the user retype the preset** — rejected: the directory entry already knows the endpoint, the protocol, and the models a picked preset ships. Dropping them on the floor makes the add flow a transcription exercise; seeding the draft is one read of fields the page already holds.
- **Ship logos as image assets resolved by route id alone** — rejected: the route set is open (hand-declared gateways have no mark), and a provider may want a different mark than its route suggests. The vendored set plus the profile's `icon` field gives shipped routes their own marks, custom routes a choice, and unknown routes the letter avatar.
- **A silent no-op when every row is filled** — rejected: a disabled button that names its reason (`mappingFull`) says what to clear; a button that closes the dialog having written nothing would read as success.

## Consequences

- The pi-ai surface lost its add-row command, capacity disclosures, and modality toggles; the DeepSeek family keeps its table posture (`DeepSeekModelsEditor`), so the two families' model editors now differ in kind, not just in extras — a catalog is curated, a mapping is assigned.
- A stored profile whose entries name other things is preserved through an edit but never visible on the card; the write gate still judges those entries, so an invalid invisible entry fails the write with its array position.
- The create card's "at least one mapped model" gate now reads as "fill any of the six rows" — the bare fallback entry alone is a valid creation, sized by the route's fallbacks.
- The directory payload grows with the catalog: every dormant route carries its models to the browser even before it is configured, and the add dialog renders those facts as a prefilled form.
- The vendored icon set is a maintenance fact: a cc-synced update re-vendors `provider-icons.ts` wholesale, and an unknown icon name in a stored profile falls back to the letter avatar rather than failing.
- The fetch dialog's probing state, empty listing, and rejected transport each surface in the dialog while the rows wait behind it for hand-entry — a provider that cannot be interrogated is a detour, not a dead end.
- The reply is a fact the form keeps, not just a dialog state: the fetched pool outlives the dialog (a second open re-asks, refreshing it), and the banner/latency report is the only feedback a long listing gives that it worked at all.
- The embedded add flow's pick and edit dialogs render footer slots that the two forms portal their cancel/commit rows into (the [embedded-form note](2026-08-28-models-add-dialog-embedded-form.md) owns that posture); the mapping and its dialog ride inside the same dialogs unchanged.

## Verification

- `provider-form.client.spec.tsx` — the `model mapping` cases: each filled row stores the entry the adapter serves it under (`role` on the entry, the name separate); a stored profile reads back into its rows in both spellings; the later row is named when two share one id; inherited/customized meta and emptying-vs-reset stay distinct. The `fetch model list` cases: the endpoint the form shows is asked with a key not yet stored; the protocol the profile names is carried; the base-URL field's own 管理与测试 opens the same interrogation; the banner reports the fetched count and the round-trip time; a row fills in one click from its pick menu — id, display name, the 1M declaration, the disclosed capacities — and the write carries them; only picked candidates are adopted, keeping a row the user already tuned and its display name; the five roles fill in order and the fallback last; adoption is refused when every row is filled; the rows stay editable when the provider cannot be interrogated; an empty listing and a rejected transport are reported; a configured route is askable with no endpoint; the create card asks only once it has an endpoint; cancel closes without adopting; a candidate toggles off and back on; select-all and clear-all act in one gesture. The field-scoping case pins the form order — logo, identity, endpoint, key, mapping on the form, the rest folded behind 高级选项.
- `components.client.spec.tsx` — the card/avatar case now asserts both marks: a route the icon set has no mark for wears the letter avatar, a route it knows wears the vendored SVG; the add flow is pinned through the embedded custom form and the editor's footer slot. `styles.client.spec.ts` pins the mapping-row (five content-free tracks, identical in the caption and every row), field-head, scrollbar-gutter, and full-width select stylesheet contract.
- `llm-pi-ai` `dynamic-config.spec.ts` asserts the directory entry carries `catalogBaseURL`, `catalogApi`, and `catalogModels` for a shipped route; the type is pasted verbatim in [llm-streaming](../../../../docs/subsystems/llm-streaming.md) under `type-equiv`, and the generated Cordis type catalog is refreshed with it.
