## 0. 决策汇总

以下为本版锁定的**载荷性决策**。它们决定架构走向,任一变更都会引发连锁返工;在首个付费客户之前尽量避免更改。每条附推荐理由与可选替代。

| # | 决策 | 本版决定 | 关键理由 |
|---|---|---|---|
| D1 | 交付形态 | **SaaS 托管先行**;企业自托管作为二期架构预留 | 迭代快、能直接感知用户;跨租户隔离统一做一套 |
| D2 | 多租户隔离边界 | **按"工作区"共享运行时**,租户物理边界可选 | MVP 可水平扩展、成本可控;隔离语义由工作区归组 |
| D3 | 引擎嵌入方式 | **进程内嵌,接口上预留进程外** | 数据面打通 + 权限直插;MVP 最快,未来可切 SDK/ACP |
| D4 | C 端执行深度 | **精选受管能力先行**;真实执行按能力灰度开放 | 安全可控、成本低;把执行模式做成能力属性 |
| D5 | 能力封装规范 | **复用 dsh 插件 + preset + schema 化资产** | 生态飞轮的基础;避免自造元模型 |
| D6 | 审批分层 | **业务审批(状态机)与 AI 执行审批(interaction)分离** | 避免流程与权限纠缠 |
| D7 | 数据面血缘桥 | **业务对象表 ↔ session log 事件通过引用关系互联** | 核心卖点"可追溯"的机制落点 |
| D8 | 权限强制点 | **在 provider 边界强制,而非 UI 层** | "角色只能看该看的"不能靠 UI 隐藏 |

**产品决策(已由需求方确认):**
- 交付形态:SaaS 托管先行
- 首发形态:B 端产研一体先行(C 端作为后续自然延伸)
- C 端执行深度:精选受管能力先行

**本版明确不做(防止范围膨胀):**
- 不做真正的低代码/自研应用引擎(C 端用户搭出"给他用户用"的应用)——那是独立工程,等组合式 preset 市场验证后再评估。
- 不在一期实现企业私有化交付(部署拓扑在架构上预留,但产品/运营支持不建)。
- 不在一期实现 C 端计费/结算(能力市场目录先建,计费后接)。

## 1. 产品形态与定位

**一句话定位:多租户的 AI 运行时 + 能力市场 + 协作控制面。**

- 产研一体是首个**旗舰能力套装**(垂直示例),不是产品本身;
- 平台"能力即插即用"的机制 = dsh 的插件/preset 机制本身,被产品化为可组合、可交易、可追溯;
- 不同角色(产品/UI/开发/测试)共用统一资产空间与统一血缘,各角色经预设获得不同的工具面。

### 1.1 三个角色集群(用户画像)

| 角色集群 | 代表 | 期望能力 | 交付形态 |
|---|---|---|---|
| 运营方 | 平台团队 + 能力创作者 | 上架能力、管理市场、审计 | 平台后台 |
| 创作者(专业用户) | 产研团队、内容创作者 | 组装能力、搭场景、协作 | 场景工作台 |
| 终端用户 | 学生、短视频创作者 | 用预设好的能力完成目标 | 轻量工作台 |

### 1.2 产品分层

```
┌─ 场景层(可插拔):  产研一体 | 创作者套件 | 学习助手 ...
│                  每种 = 预设 + 资产schema + 专属桥插件
├─ 能力市场层:      目录 | 依赖/冲突检查 | 版本 | preset装配器 | 计费(二期)
├─ 控制面:         身份/租户/RBAC | 资产仓库+血缘 | 业务审批流 | 审计 | 计费(二期)
├─ 引擎适配层:      角色→preset翻译 | 业务对象↔session log血缘桥 | ACL→provider策略
├─ 运行时:         dsh引擎(agent-loop/subagent/workflow) | 沙箱 | session log
└────────────────────────────────────────────────────────────────────────────
```

## 2. 载荷性决策详述

### D1 交付形态:SaaS 托管先行

- **决定**:统一运营一套 SaaS,所有租户共享平台代码。
- **架构预留**:把"部署拓扑"(单区/多区、自托管、混合)做成**配置**而非代码,通过 `deploymentMode` 驱动差异;未来企业自托管不重写平台。
- **原因**:MVP 阶段迭代最快、能直接收集真实反馈;跨租户隔离只需做一套统一方案。

### D2 多租户隔离边界:按"工作区"共享运行时

- **决定**:**多租户共享一套运行中的 dsh 进程树**,以**工作区(workspace)为隔离单元**。一个工作区 = 一个项目/团队,持有自己的角色集、资产子空间、preset 绑定。
- **隔离语义由工作区归组决定**:
  - 每个工作区的 agent 会话绑定到一个**独立运行时上下文**(独立 `ctx.agents` 实例或独立会话域);
  - 跨工作区访问被路由策略拒绝。
- **租户物理边界可选**:
  - 默认所有租户共享同一进程树;
  - 需要物理隔离的租户(大客户/合规)可分配到独立进程/容器。
- **原因**:MVP 可水平扩展、成本可控;"每个角色一个隔离实例"的干净表达改为"每个工作区一组角色会话",安全模型更简单。
- **风险**:共享进程下,若某个工作区的 agent 跑出问题可能影响同进程其它工作区。缓解:运行时对工作区做资源配额(并发、队列、内存),并允许按需拆进程。

### D3 引擎嵌入方式:进程内嵌,接口上预留进程外

- **决定**:MVP 将 dsh 作为**同一进程内的库**装配(`ctx.plugin(...)`),引擎适配层在进程内把角色/权限/资产上下文翻译成 preset 配置并注入。
- **进程外预留**:在适配层上定义**驱动接口**(`DriveAgentRun` / `ListSessions` / `ReadLog`),使未来可切换为独立 dsh 进程(通过 SDK / ACP 驱动)。
- **原因**:进程内便于数据面打通、权限直插强制点、MVP 最快;进程外(每角色/每工作区独立实例)是未来隔离与升级隔离的更优形态,但成本更高。
- **迁移路线**:MVP 用进程内 → 若多租户隔离/稳定性要求升高,将驱动接口换成 SDK/ACP 进程外实现。

### D4 C 端执行深度:精选受管能力先行

- **决定**:C 端用户使用**平台托管的能力**(生成/分析/编排/检索/桥接),**不直接暴露** `fs`/`subprocess` 全权。
- **执行模式作为能力的一个属性**(`execution: managed | sandboxed | none`):
  - 默认 `managed`(平台调度);
  - 特定高级能力(沙箱验证过的)允许 `sandboxed`(受限真实执行);
  - 按能力灰度开放。
- **原因**:安全可控、成本低;dsh 的本地沙箱(Landlock/bwrap)是单机设计,云端多租户下真实代码执行是硬骨头,放到二期。

### D5 能力封装规范:复用 dsh 插件 + preset + schema 化资产

- **决定**:平台能力 = **dsh 插件(工具/服务)+ 预设(角色工具面)+ 资产 schema(数据形态)** 三者统一打包。
- **原因**:生态飞轮依赖标准封装;dsh 已有成熟插件模型与 preset 机制,避免自造元模型。
- **接口**:
  - 插件通过 `ctx.tools` / `ctx.effect()` / `ctx.waterfall()` 注册;
  - 预设通过 `agent.cordis.yml` 声明角色工具面;
  - 资产 schema 通过 merge-extensible 注册。

### D6 审批分层:业务审批与 AI 执行审批分离

- **业务审批**(立项、需求评审、上线放行):**平台控制面自建状态机/工作流**,不依赖 dsh。
- **AI 执行审批**(agent 要执行敏感操作):用 dsh 的 `interaction`/approval 缝,作为业务审批之下的一层执行保护。
- **两层串接**:业务审批放行 → AI 拿到授权范围 → AI 敏感操作再过执行审批。

### D7 数据面血缘桥:业务对象 ↔ session log 互联

- **核心卖点"可追溯"的机制落点**。
- session log 的 AI 行为可**引用业务对象 id**;业务对象表记录血缘关系。
- 于是"这份代码变更 → 实现了哪条需求 → 来自哪版 PRD"跨角色可追溯,且**构造性保证**(任何模型可见输入都来自 session log)。
- **机制**:在 session event 中写入业务对象引用(id + type + role),在业务库建立 lineage 关系表。

### D8 权限强制点:provider 边界强制,而非 UI 层

- **UI 隐藏不构成权限**。真正的强制点在 provider 边界:
  - `fs`/`sandbox` policy 缝接入你的 ACL(角色 → 可读写路径/工作区);
  - approval 缝作为 AI 敏感操作的执行保护;
  - 适配层将 ACL 语义注入 provider 策略。
- **原因**:模型直接持有 `fs`/`subprocess` 工具,UI 层藏不住。

## 3. 目标架构

### 3.1 五层架构

```
┌──────────────────────────────────────────────────────────────┐
│ 场景层 (可插拔,一期=产研一体)                                    │
│   预设(角色工具面) | 资产schema | 专属桥插件                     │
├──────────────────────────────────────────────────────────────┤
│ 能力市场层                                                      │
│   目录 | 依赖/冲突检查 | 版本 | preset装配器 | 计费(二期)          │
├──────────────────────────────────────────────────────────────┤
│ 控制面                                                          │
│   身份/租户/RBAC | 资产仓库+血缘 | 业务审批流 | 审计 | 计费(二期)  │
├──────────────────────────────────────────────────────────────┤
│ 引擎适配层                                                      │
│   角色→preset翻译 | 业务对象↔session log血缘桥 | ACL→provider策略 │
├──────────────────────────────────────────────────────────────┤
│ 运行时                                                          │
│   dsh引擎 | 沙箱 | session log                                  │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 多租户拓扑

- 共享运行时 + 按工作区归组隔离。
- 工作区持有:角色集、资产子空间、preset 绑定、成员表。
- 可选物理隔离(大客户/合规):分配到独立进程/容器。

### 3.3 四个数据面

| 数据面 | 内容 | 归谁管 |
|---|---|---|
| 业务对象库(关系库) | 需求、资产、审批单、角色、工作区 | 平台自建 |
| AI 执行日志 | session log(每次 AI 思考/工具调用/输出) | dsh |
| 对象存储 | 设计稿快照、大文档 | 指针 |
| 检索索引 | 全文/向量,给 AI 做 RAG | 派生(session-query FTS 已有种子) |

**血缘桥**:session log 的 AI 行为引用业务对象 id;业务库记录 lineage 关系 → 跨角色可追溯。

### 3.4 身份与 RBAC

- 平台自建:租户、成员、角色、角色-权限映射。
- 工作区归属决定可见资产子空间。
- **不修改 dsh 的 identity**(匿名单用户);平台身份在适配层翻译成工作区/角色上下文。

### 3.5 能力封装与组装

- 能力 = 插件 + 预设 + 资产 schema。
- 用户按喜好组装能力 → 适配层渲染为 preset 配置 → 挂载到对应 agent 会话。
- 能力市场提供目录、依赖/冲突检查、版本。

### 3.6 引擎适配层职责

- 角色 → preset 翻译:把角色 + 权限 + 资产上下文翻译成 `agent.cordis.yml`。
- 业务对象 ↔ session log 血缘桥:写入业务对象引用、读取血缘关系。
- ACL → provider 策略:把角色权限注入 `fs`/`sandbox` policy 缝。

## 4. 安全模型

### 4.1 强制点

- **provider 边界**:`fs`/`sandbox` policy 缝注入 ACL;`approval` 缝作为 AI 敏感操作保护。
- **会话隔离**:工作区级隔离,跨工作区访问被路由策略拒绝。
- **身份**:平台身份与 dsh 匿名 identity 分离。

### 4.2 沙箱

- MVP:C 端 = 精选受管能力,无直接 `fs`/`subprocess` 全权;受限执行用 sandbox 后端(Landlock/bwrap,进程级)。
- 二期(如需真实执行):评估云端沙箱/容器隔离。
- **安全底线**:把"执行模式"做成能力属性,按能力灰度开放,而非全局放开。

### 4.3 数据保护

- 对象存储指针 + 权限校验;审计日志记录访问。
- session log 的读访问受工作区/角色约束(经血缘桥授权)。

## 7. 路线图(分四期)

### 一期(MVP,验证核心机制)
- 平台壳:登录/租户/RBAC、资产仓库(+血缘)、业务审批流、审计。
- 引擎适配层:dsh 进程内嵌、角色→preset、血缘桥、ACL→provider。
- 产研一体场景:需求→设计→开发→测试→上线单条纵切。
- 能力市场:目录雏形(预设装配,不计费)。

### 二期(扩展到 C 端自组装)
- 能力市场完整化:依赖/冲突检查、版本、计费/结算。
- C 端轻量工作台:用户按喜好组装能力。
- 受限执行(按能力灰度开放)。

### 三期(规模与隔离升级)
- 按需物理隔离(大客户/合规)。
- 引擎进程外化(若隔离/稳定性要求升高)。

### 四期(评估低代码)
- 组合式 preset 市场验证通过后,评估"用户搭给用户用"的低代码方向。

## 8. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 预览版依赖:dsh 无稳定 API 承诺,`SESSION_FORMAT_VERSION` 恒为 0 | 高 | 锁版本;必要时 fork;设计上用适配层隔离 dsh 变更;`terminator` 分支同步策略 |
| 云端多租户执行 + 沙箱安全(C 端真实执行) | 高 | C 端精选受管能力先行;真实执行二期;沙箱走进程级 Landlock/bwrap |
| 共享进程下工作区相互影响 | 中 | 资源配额;按需拆进程 |
| 资产治理域深度(版本/关联/权限/lifecycle) | 中 | 一期先做"指针+关系",不做文件搬移 |
| 权限强制点执行不彻底("角色只能看该看的") | 高 | 强制点下沉 provider 边界;T4 验证 |
| 跨角色协作协同(实时编辑设计稿/文档) | 低 | 一期不做实时协同;用"各自轨道 + 产物交接" |
