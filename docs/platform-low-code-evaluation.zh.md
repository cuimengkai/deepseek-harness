# 低代码方向评估

[English](platform-low-code-evaluation.md) | 中文

> [platform-architecture.md](platform-architecture.zh.md)(§7 Phase 4、D5)的配套文档:这是 Phase 4 对「用户为用户构建」这一低代码方向的评估。它盘点 Phase 2、3 已验证的可组合预设市场,指出非工程师装配路径的关键缺口,并记录所选机制。

## 1. 前提

路线图的 Phase 4 是「评估用户为用户构建的低代码方向」。就本产品而言,这意味着一个客户群用户装配一个工作台——一组能力、一个预设绑定与一个人设——供同群其他用户运行,而无需手写 agent 组合。路线图把评估的前提设为可组合预设市场已验证;Phase 2 与 3 交付了这一验证([能力市场](platform-capability-market.zh.md)、[引擎隔离](platform-engine-isolation.zh.md))。

## 2. 装配单元本身已具低代码形态

工作台是一个场景捆绑:一个按客户群区分的描述符,指明一组能力、一个预设绑定与一个人设,经 `publishScenario` 发布并由 `roster.mount` 提供。市场已校验该集合——依赖顺序、版本范围、冲突对与执行门禁都响亮拒绝,不会静默跳过任何一项——计费也按工作区计量消费。工作台「是什么」已经确定且经机器校验;缺失的是产生这样一个捆绑的非工程师路径。

## 3. 关键缺口,现已闭合

预设装配器设计([platform-preset-assembler.md](platform-preset-assembler.zh.md))定义了这一步:把一个角色、一组所选能力与上下文变成一棵可运行的预设树,并在 roster 挂载前完成校验。这一步曾是缺口:工作台要到达 roster,只能通过手写的角色预设或操作者驱动的 agent 调用。渲染与「校验后提交」步骤现在已在 `@deepseek-ai/dsh-experimental-platform-shell` 中实现,并由 capability-market demo 的引导式构建无密钥证明:非操作者创建者 agent 调用 `assemble_preset`,平台渲染并校验树,宿主把行提交到 roster。仍把非工程师与「用户为用户构建」隔开的,是描述符的创作表面,而不是装配机制。

## 4. 候选机制

- **声明式工作台描述符。** 用户把捆绑描述符当作数据来编写或编辑——id、显示名、角色、预设 id、能力 id、各能力选项、人设。市场校验集合,装配器渲染预设树,roster 挂载它。这是严格意义的低代码:创作单元是描述符,而不是 `cordis.yml` 行。
- **模型引导装配。** capability-market demo 中的操作者 agent 已经通过 `publish_capability` 与 `publish_scenario` 调用构建工作台。模型引导路径把它变成一个交互式构建工作流:用户描述团队需求,平台 agent 选择能力、执行解析,并发布校验通过的捆绑。这是无头构建工作流。
- **可视化构建器。** Web 应用里拖拽式的工作台构建器。市场 spec 已把页面渲染划给 Web 应用层;这个机制增量最大,是无头机制验证后的自然后续。

## 5. 必须补齐的缺口

- **各能力选项**——用户如何在不动预设行的前提下配置一个能力的选项。
- **用户侧工作台生命周期**——草稿、校验、发布、回滚;`publishScenario` 只覆盖注册,不覆盖它周围的构建工作流。
- **治理边界**——用户装配,操作者发布能力;门禁、灰度与计费仍是执行点。

## 6. 所选机制

把声明式描述符加上模型引导装配作为低代码机制推进,把可视化构建器推迟到 Web 应用层。描述符与发布/装配工具已存在且经无密钥验证;装配器的渲染与「校验后提交」步骤已经实现,capability-market demo 驱动了一个引导式构建:非操作者创建者 agent 无密钥地从意图走到一个已挂载的工作台。剩余构建块是各能力选项表面与用户侧工作台生命周期(§5);治理边界保证低代码的安全。

## 7. 风险

- C 端真实执行仍是架构风险表中列出的高风险;受管能力集与执行门禁对其加以约束。
- 治理漂移——低代码必须让用户装配,绝不允许发布新能力;发布路径保持操作者专属。
- 构建规模——模型引导工作流是可无密钥验证的第一形态;可视化构建器改变的是呈现而非机制,并增加产品范围。
