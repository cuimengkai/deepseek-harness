# @deepseek-ai/dsh-host-plugin-manager

English | [中文](README.zh.md)

Live install/uninstall of plugins for the Web console, including real network installs from configurable catalog sources. `PluginManagerGateway` registers the `pluginManager` service and publishes four generated direct Remotes: `pluginManager/listAvailable`, `pluginManager/refreshCatalog`, `pluginManager/installPlugin`, and `pluginManager/uninstallPlugin`. Public payload types live under `./types`; the service is Remote-only and declares no same-process Cordis `Context` merge, so client packages consume it through the explicit [`api-remotes`](../../api/remotes/README.md) assembly rather than importing the Host implementation.

`listAvailable` reads a merged catalog from the configured sources (`Config.sources`), runs each network source through the list-time validation gate (§Validation and trust), and marks each surviving entry `installed`. `refreshCatalog` re-fetches every network source bypassing the cache. `install` looks the requested name up across the merged catalog — through the same gate, so a dropped entry is not installable by a direct call — and either commits a managed home-patch row for a locally-resolvable module or runs a contained package-manager network install before committing the row; the running Host's config-HMR watcher recomposes and the root Include mounts the fiber without a restart. A name in no catalog source falls through to the bundled spine: a disabled harness plugin is reinstalled by clearing its disable override. `uninstall` removes exactly the managed rows (Loader entry id `dsh-managed-<slug>` with the matching module name) and, for a network install, the store, symlink, and ledger entry; a bundled harness plugin gets a persisted `disabled: true` override instead (patches cannot delete rows, so enablement is the reversible switch); user-authored rows, bundle or profile patch layers, and other modules are never touched. Every committed install or uninstall and every `refreshCatalog` emits the `plugin-manager/catalog-changed` Host event (coalesced per frame), which the [`api-remotes`](../../api/remotes/README.md) forwarding loop relays to clients that subscribe.

## Config

`Config.sources` is a list of source descriptors, merged in order. The shipped default is the awesome curated list plus the GitHub `dsh-plugin` topic search. The legacy `catalog` option is accepted and normalized to one `static` source when `sources` is absent. The `static` kind holds an inline list of locally-resolvable modules (the v1 surface, installed with no network step). The `awesome` kind fetches the awesome-dsh-plugin curated list as its repository tarball and parses `data/plugins/*.yml` locally; each entry installs by its GitHub `user/repo` spec. The `topic` kind runs a GitHub repository search, probes each repo for npm-installability, and shows only the installable ones (a repository with a root `package.json` whose name is valid and not `private`); unproven and non-package repos are dropped at list time, never shown browse-only. The `manifest` kind fetches a generic JSON manifest (an array, or `{ entries: [...] }`) at `url` and is the documented extension point for a private marketplace; each entry's `ref` is the npm install spec, defaulting to the entry `name` when absent.

Network behavior is deployment policy: `offline` skips all network fetches and installs and serves only cached and static entries; `installPrefix` moves the install root away from the default `$DSH_HOME/profiles`; `packageManager` names the executable (default `npm`); `fetchTimeoutMs` bounds each manifest fetch (default `30_000`); `cacheTtlMs` overrides the per-kind cache TTL (the `topic` default is 15 minutes to stay inside GitHub's anonymous budget).

Install safety is also deployment policy, all changeable from `cordis.yml`:

- `installSandbox` (default `true`) runs every network package-manager invocation under the OS sandbox with a `workspace-write` file policy. When enabled but no backend is usable the install is refused with `sandbox-unavailable` — the package manager never runs unconfined.
- `allowInstallScripts` (default `false`) permits lifecycle scripts at all; `--ignore-scripts` is appended to every install unless this config AND the per-request `allowScripts` are both true.
- `requireInstallConfirmation` (default `true`) makes the Host refuse a network install whose request lacks an explicit `confirmed: true` (`confirmation-required`); the check is host-side, so bypassing the console still hits it. Static and bundled installs are reversible local operations and never require confirmation.
- `validationProbeBudget` (default `10`) caps how many uncached repositories one catalog pass may probe for npm-installability, and `validationProbeTtlMs` (default 24 h) decides how long a cached verdict stays fresh. Both exist because GitHub's anonymous contents API is tightly rate-limited.
- `probeAwesome` (default `false`) extends the npm-installability probe to `awesome` entries; the curated list is trusted by default.

## Validation and trust

List-time filtering is a server-side policy module (`src/validator.ts`), applied both when a snapshot is built and inside `findInstallable`, so the console cannot be bypassed by calling install on a name the list already dropped. Every non-`static` entry first passes a syntax gate: `topic`/`awesome` names must match `owner/repo`, and a `manifest` entry's `installRef` must be a safe npm spec (bare name, `@scope/name`, `user/repo[#branch]`, or a public `https`/`git+https`/`github:` URL) — `file:` and other local-path schemes are refused outright. Then the npm-installability probe reads each repo's root `package.json` through GitHub's contents API; a 404 (no manifest, or a private repo) is `not-installable`, rate limits and server errors are `unknown`, and both are dropped rather than shown. Verdicts persist in `$DSH_HOME/plugins/cache/probes.json` with a freshness TTL, so once a repo is probed a later refresh usually probes nothing. Each source reports how many entries it dropped through `filteredCount` on `PluginManagerCatalogSourceStatus`, so the console can show that filtering happened instead of silently hiding entries. Offline sources skip the probe and keep their entries browse-only, so an offline console still shows what its cache holds.

## Network install and uninstall

A network install builds a per-plugin store at `<installPrefix>/node_modules/.dsh-plugins/<slug>/` — an isolated npm project with `--legacy-peer-deps` explicit — runs the package manager on the entry's `installRef` (lifecycle scripts off by default, under the OS sandbox, with npm's cache redirected into `<slugDir>/.npm-cache` so the uninstall deletes it with the store), discovers the resolved package name, and symlinks `<installPrefix>/node_modules/<name>` to the store module. The store sits under the healed `profiles/node_modules` fallback, so the installed plugin's peer imports (`@deepseek-ai/cordis`, Service Definition packages) resolve by Node's parent walk to the Host's single cordis rather than to a duplicate npm-installed copy. The resolved name, version, and npm integrity are recorded in the provenance ledger `$DSH_HOME/plugins/installed.json`, then the managed home-patch row is appended so HMR mounts the fiber; a collision with an already-mounted or already-managed resolved module is reported `already-installed` after the package manager ran. The catalog snapshot carries a `capabilities` block (`networkConfirmation`, `allowInstallScripts`, `installSandbox` as `confined`/`unconfined`/`unavailable`) so a client renders exactly the trust surface the deployment permits.

`uninstall` removes the managed row first (unmounting the fiber via HMR), then the symlink, store, and ledger entry. A network store is verified against the ledger before removal — an integrity drift is reported in the result's warning path but the store is still deleted completely, because a suspected tampered plugin is exactly the one that must be removed. When the user took over the module's row, the store and ledger are kept so the module keeps mounting and the provenance survives, and the call reports `not-managed`. A cleanup failure after the row is gone returns `remove-failed` and leaves an orphan a retry cleans.

Rejection codes: `invalid-name` (the specifier is not a bare module name), `invalid-entry` (the catalog entry failed the list-time validation gate), `not-found` (the name is in no source and no bundled spine entry), `offline` (network installs disabled), `already-installed`, `not-installed`, `not-managed`, `in-use` (the module is part of the plugin-manager's own runtime base and cannot be disabled in-process), `confirmation-required` (a network install without the explicit trust confirmation), `sandbox-unavailable` (sandbox confinement requested but unusable — the package manager never ran), `install-failed` (the package manager or store setup failed, stderr tail in `message`), and `remove-failed`. The install response is a point-in-time snapshot of the committed row — the mount lands asynchronously, and the console re-reads the inventory to observe the outcome.

## Known Limitations and Deferred Work

- **Community installs execute third-party code in-process** — a network install runs the plugin's own code inside the Host process; `--ignore-scripts` and the OS sandbox contain the install step, and the explicit trust confirmation and integrity ledger give the operator evidence, but no process boundary isolates a malicious plugin at runtime. Real runtime isolation (a subprocess plugin host) is a later architecture phase; until then, installing an unvetted package is the operator's decision.
- **GitHub sources are rate-limited** — the topic search and npm-installability probes share GitHub's anonymous budget (roughly 60 requests an hour). The 15-minute topic cache and the probe verdict cache absorb it; a hard refresh can still hit `403`, surfaced per source in `listAvailable` with a `filteredCount` for the entries the budget left unprobed.
- **No version pinning** — a topic or awesome entry installs the current repository HEAD (`npm`'s GitHub shorthand); the ledger records the resolved version and integrity, not a frozen SHA. A manifest source can pin by shipping an explicit tarball `ref`.
- **Integrity is a store-level check, not a package signature** — the ledger compares the current `package-lock.json` against the recorded npm integrity, so it detects local drift, not a compromised upstream registry or an author changing a published tarball.
- **Peer-sharing relies on the profiles fallback** — `--legacy-peer-deps` skips npm's peer auto-install so peers resolve through the healed `profiles/node_modules`, which requires the install prefix to sit in that parent-walk; moving `installPrefix` off the default breaks the sharing and npm would install a duplicate `@deepseek-ai/cordis`.
- **Managed rows never overwrite user rows** — `uninstall` removes only rows whose Loader entry id carries the `dsh-managed-` ownership marker and whose module matches; a user-authored row for the same name is left in place and reported as `not-managed`.
- **Bundled "uninstall" is a persisted disable, not row deletion** — patches cannot delete rows, so uninstalling a shipped harness plugin writes a `disabled: true` override on its bare row id and installing again clears it (`disabled: false`); both are fully reversible and idempotent. The plugin-manager, plugin-inventory, and the API/typert gateways that carry the manager's own wire calls are fixed in the irreplaceable set and refuse uninstall with `in-use` — the manager cannot disable the hand that executes the request.
- **Escaping the safety defaults is a deliberate deployment choice** — `installSandbox: false` and `requireInstallConfirmation: false` remove the refusal gate entirely; an operator who sets them takes over the risk the defaults carry.
- **Rewrite drops YAML comments** — the locked read-modify-write re-serializes the home patch through the Loader entry-list schema, so hand-authored comments in `$DSH_HOME/cordis.patch.yml` are not preserved.
